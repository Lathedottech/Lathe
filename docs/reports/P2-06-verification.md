## 3. Technical decisions
- Operations are `{principal, action, resource}` indexes generated by fast-check and sent through the contract routes. Rejected: calling app code directly (suites may know an app only through C1).
- The seed defaults to a hash of run id and app name, and is always in the result. Rejected: fast-check's random seed (not reproducible).
- Reproduction is by seed plus run count on a freshly started app. The shrunk `path` is logged but not replayable alone, because the app keeps state across runs (the fixture ids depend on request order). Rejected: a `replayPath` option, which would promise something false.
- Fixture ids are deterministic (counter based), so a re-run issues identical requests.
- Pending invariants appear in the result, the gate summary and as `info` findings. They never add to passing checks. The gate status depends only on violations. Rejected: failing the gate on pending, which would block every run.
- `propertiesGate` is not added to the default registry (no app launcher until P2-08), same as `rbacGate`.
- Known-bad fixtures: `leaky-by-id` (viewer may update and delete only on ids starting 0-7) and `collision` (org check skipped for an id two orgs both created).
